# 决策日志

**怎么写这个文件**：新条目加在**最上面**（倒序）。每条包含四样东西 ——
**日期 / 决定 / 理由 / 代价**。

代价那一栏不许留空。一个只写了理由的决策记录，半年后会看起来像"免费的"，
而实际上每个决策都有代价 —— 忘了代价，就会在下一次重复付一遍。

写这个文件的原因是：2026-10-16 抽取独立仓库时发现，这个项目此前**所有重要决策
都只存在于当时的对话里**，仓库里一个字都没有。

## 2026-10-16 · 项目从研究仓库抽取为独立仓库 `pumpidea`

**决定**：把原研究仓库（同时装着 Stableflow 线与 pump.fun 线）里的 `pumpfun/`
抽取为独立仓库 `pumpidea`（`git@github.com:aidai524/pumpidea.git`）。
原仓库**冻结、零写入**（`git subtree`/`filter-branch` 在克隆副本里做）。

**理由**：两条线互不相干；pumpfun 已长出四条子线（analysis/audit/risk/pulse）、
25 个提交、一台常驻 VPS，不该再待在"研究仓库"的子目录里。而且 web 会引入新顶层，
先抽取再做 web 可以少改一遍所有路径。

**代价**：抽取时唯一存在的代码级耦合是 `analysis/jev_score.py` 读 `../platform/.env`
取 `TYPESAFE_API_KEY` —— 已改为读本仓库 `.env`。另外 pi 的会话归档按 **cwd 路径**
命名（`~/.pi/agent/sessions/--Users-joe-Any-analysis--/`），项目移动后**不会自动关联**；
所以本项目改用**这份文件**承载决策记忆，不依赖对话归档。

## 2026-10-16 · 统一站点采用 React SPA + 薄 BFF（**有意的例外**）

**决定**：在 `pumpidea` 内建 `web/`（React + TS + Vite + Tailwind v4）与
`api/`（FastAPI 薄 BFF，暴露 `/api/v1/*`），单一入口经 Caddy 路径路由。

**理由**：四个服务目前是四个互不相连的页面/端口，没有统一入口、没有可长期维护的前端。
BFF 的价值在于：把各服务内部字段的差异挡在后端（前端只认契约）、统一鉴权、
**服务端持有 risk 的凭据**（浏览器不接触）。

**代价**：**这是对本仓库"运行时零依赖"约定的有意偏离**（约定见 `AGENTS.md` §5）。
引入 node 工具链、一套前端范式、CI 构建产物。之所以值得，是因为定位是"产品前端"
而不是一次性研究页；但**除 web 之外不得再引入前端框架**。为控制代价：
不引第三方图表库（把现有手写 SVG 移植成组件）、产物由 CI 构建并提交、VPS 上不装 node。

## 2026-10-16 · 存储分层：JSON 是**服务格式**，不是存储

**决定**：`analysis/facts.json`（40KB，批处理产物）与 `audit/stream_report.json`、
`pulse/site/data.json`（服务格式）**保持 JSON**；原始事件只留**滚动窗口**，
聚合结果永久保留（"先聚合、后丢弃"，P6）。**不换数据库引擎。**

**理由**：四个数据面里三个**已经在用 SQLite 做存储**（12 处 `sqlite3.connect`），
JSON 全是生成脚本写出来的**产出物**（`analyze.py:283`、`stream_report.py:346`、
`builder.py:91`）。所以"JSON 存储不行"这个判断的**问题不在 JSON 上**。
真正的问题是四个互不相通的 SQLite 文件 + 并发写 + 运维职责无人归属 + 体量。
换 Postgres 会让体量**更大**（行头/索引/TOAST），还会绑死一个引擎。

**代价**：要重做保留策略（原始事件 7 天 → 48 小时），并把 WAL/保留/备份的
运维职责收到**一个任务与一个日志**里。磁盘账：7 天 × 8G/天 = 56G，叠加 Plane 的
27.3G ≈ 83G > 78.3G 原盘 —— 也就是说**旧配置本来就装不下**（这是除 WAL 之外的第二颗雷）。

## 2026-10-16 · 修掉两个既有缺陷（都在 `risk/score_service.py`）

**决定 1 —— HTML 模板花括号**：`DEMO_PAGE` 是**普通字符串**（`"""`）而非 f-string，
但里面的 JS 用了 f-string 风格的双花括号 `{{` / `}}`，被原样吐进 HTML →
内联 `<script>` 语法错误 → `go()` 从未定义 → **评分按钮点击完全没反应**（静默
`ReferenceError`）。修法：还原为单花括号。

**决定 2 —— 历史库缺失时报错费解**：`sqlite3.connect()` 在文件不存在时会
**悄悄建一个 0 字节空库**，于是"还没建库"被伪装成 `no such table: creators`。
修法：改**只读**打开（`mode=ro`）、启动时校验 `creators` 表存在、缺失即打清晰告警
并按"无历史"降级（该降级路径本来就有，只是对"表不存在"没兜住）。

**代价**：无（纯修缺陷）。教训：**同类不对称要当成信号** —— 同一文件里
`STREAM_HISTORY` 有 `.exists()`+try/except 保护，主库却裸着。

## 2026-10-15 / 10-16 · WAL 事故：两次把磁盘打满（**本项目最贵的一课**）

**现象**：`stream.sqlite3-wal` 先涨到 **33.55G**（10-15），修复后仅约 7 小时又涨到
**35.5G**（10-16）。两次都是磁盘 100%、采集器
`sqlite3.OperationalError: disk I/O error` 崩溃、静默停摆数小时（3.4h / 16h）。

**根因链（三层叠加，缺一不会发生）**：

1. 库是 WAL 模式，但**代码里没有任何地方设置或管理它**（`grep journal_mode` 在
   `/opt/pumpfun-stream` 零命中）。WAL 模式一旦设定就永久记在库头里。
2. **WAL 文件只涨不缩** —— 它是高水位，只有 `wal_checkpoint(TRUNCATE)` 才会缩回；
   默认的自动 checkpoint 只把页搬进主库，不缩文件。
3. **决定性的一层：有长时间只读分析任务在钉住 checkpoint 水位线。**
   两个任务直接跑在**写入中的** SQLite 上：

   | 任务 | 频率 | 单次耗时 | 行为 |
   |---|---|---|---|
   | `stream_report.py` | 每小时 | 7+ 分钟 | 2800 万行 GROUP BY，全程持读快照 |
   | `update_history_from_stream.py` | **每 15 分钟** | >5 分钟 | 回看 3 天**全表 + 窗口函数**，全程持读快照 |

   读占空比接近 100% → 永远找不到"无读者"的瞬间 → **WAL 永不重置** → 无限增长
   （实测 ~6GB/小时）。

**直接证据**（这是本条记录存在的意义 —— 一次 trace 看到了机制）：

```
t= 30s  WAL=1918MB  checkpoint=[busy=0 | log=488285 | checkpointed=292387]
t=210s  WAL=2313MB  checkpoint=[busy=0 | log=588733 | checkpointed=292387]   ← 水位线冻结
t=240s  WAL=2317MB  checkpoint=[busy=0 | log=    859 | checkpointed=    859]  ← 读者退出，瞬间重置
```

`checkpointed` 冻结在 292387 长达 240 秒。**注意 `busy=0` 是个陷阱** ——
"没被阻塞"不等于"水位线在前进"。

**做了什么**：

- 应急处置：把库迁到新增的 100G Linode 卷（`/mnt/pumpidea`），软链回
  `/opt/pumpfun-stream/runtime`（部署脚本路径未改）。**动手前先算空间**：
  确认 WAL 最大页号（2,774,540）**小于** DB 页数（2,864,331）→ 落盘是原地覆盖、
  文件不增长，才敢执行；并且在**副本上先验证 checkpoint 成功、数据行数一致**，
  然后才删源。结果：2886 万行零丢失。
- 调度层加固：三个周期任务全部加 **`mkdir` 原子锁防重叠**；`history` 从
  **15 分钟降为每小时**（它的 `min-age` 本来就是 1 小时，跑 4 次/小时毫无意义）；
  保留任务加 `set -e`、日志，并在空闲不足 2× 库大小时**跳过 `VACUUM`**。
- 代码层加固：`stream_collector.py` 加 `PRAGMA journal_size_limit=268435456`
  （**每连接设置，存不进库**），WAL 文件上限 256MB；
  `update_history_from_stream.py` **改为增量**（窄窗口发现 + 每 mint 走
  `idx_events_mint` 单查 + 每轮上限 + 定期重访），单次从 >5 分钟降到秒级。
- 观测：`/etc/periodic/15min/pumpfun-walwatch` 每 15 分钟记录 WAL 大小、可用空间、
  checkpoint 的 busy 读数。**它既是护栏也是证据** —— 因为失控的**最初触发点
  仍未完全确认**（第一次爆发时磁盘本来是空的），下次复发时日志会告诉我们答案。

**代价与遗留**：

- 这段记录本身就是为了不让代价重付：**任何新的重查询/写库进程，都必须先回答
  "它会持有多久的读快照"**。
- 加盘是"加大缓冲"，不是"修好根因"；根因已定位到机制层面（读者钉住水位线），
  但**最初触发条件未确认**。
- 看门狗、锁、保留策略目前**只在服务器上**，必须写回仓库的部署脚本
  （`audit/deploy/install-*.sh`），否则重装即丢。
- `PRAGMA journal_size_limit` 必须留在代码里 —— 它不是持久化设置。
