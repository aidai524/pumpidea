# pump.fun 预审计（公开数据版）

**日期**：2026-10-11
**性质**：接触前的独立诊断。不依赖内部数据，全部结论可用 `preaudit.py` 复现。
**触发点**：pump.fun 在自己的 `fees.pump.fun` 上公开声明——「自定义交易对上线后，费用看板不再正确反映收入和回购」。

---

## 0. 一页摘要（可直接用于接触）

1. **三方口径总体自洽，但差在"时窗"与"范围"**：`fees.pump.fun` 的年化收入 **$589.19M** 折合 **$1.61M/天**（自己标注是 90 天均值），而 DefiLlama 近 **30 天**合计收入 **$1.885M/天**、近 **7 天 $2.276M/天**。看板上"最新日回购 $943K"按 50% 反推的日收入是 **$1.886M/天**——**与 DefiLlama 30 天完全吻合，却与自家年化对不上**。所以问题更像"年化用旧均值 + custom pairs 未计入"，不是简单算错。
2. **他们承认的盲区有明确起点**：自定义交易对在 **2026-09-09** 上线后，非 SOL 计价发币占比从 **4~5% 跳到 10~22%**（全窗口均值 9.97%；USDC 26,403、代币化股票 23,166、其他 68,183）。**a) 公开数据能数清占比，但 b) 计不了这些曲线上的费用/收入**——这正好是他们看板出问题的区间。
3. **独立下界校验没有发现量级矛盾**：34 天里 classic 曲线的净流入（Σ`peak_rs`）为 **6.39M SOL**，对应毛手续费下界 **$8.74M**；DefiLlama 同窗口曲线费用是 **$55.20M**——**DL 是下界的 6.3 倍**。这个倍数就是"同一笔钱在曲线上反复买卖"的周转率，与既往报告的 20 倍口径（含 PumpSwap 与 32 天窗口）方向一致。
4. **custom pairs 之后周转倍数上升（5.25× → 6.01×）**：方向与"新增的非 SOL 曲线费用进入 DL 统计、但不在我们的曲线分母里"一致。**但有一个反向混淆**：09-27 解码器补全会让我们的下界变大、倍数变小，所以真实缺口只多不少。**不能据此断定他们的数字有误**——需要内部数据才能定论。
5. **独立质量基线（他们不公开的指标）**：30 天 1,212,750 个新币、毕业率 **1.98%**、瞬时捆绑占毕业 **57.2%**、有机毕业率 **0.85%**、300 秒跑路 **57.1%**；7 天口径分别 1.65% / 59.6% / 0.67% / 53.7%。

> **我们能提供的价值**：一套独立、可复现、能随时间对账的"收入与质量口径"。他们修 bug 需要的是外部参照，而不是另一份自家报表。

## 2. 对账结果

### 2.1 看板 vs DefiLlama：问题在"均值窗口"与"custom pairs"

| 口径 | 日收入折算 | 与看板的关系 |
|---|---|---|
| 看板年化 $589.19M（90d 均值） | **$1.614M/天** | 自称 90 天均值 |
| 看板最新日回购 $943.0K ÷ 50% | **$1.886M/天** | 与 DefiLlama 30d 完全一致 |
| DefiLlama 30d 收入 | **$1.885M/天** | 参考基线 |
| DefiLlama 7d 收入 | **$2.276M/天** | 当前跑速更高 |

**读法**：$943K 回购隐含的日收入与 DL 30 天对得上，说明看板的"最新"数字没问题；**年化用的是旧均值（90 天），又叠加了 custom pairs 未计**，所以对外呈现偏低。另外：累计回购 $481.46M 反推的**历史总收入约 $963M**，DL 只能覆盖近 12 个月（合计 $442.44M），更早的部分无法用免费数据独立核验。

### 2.2 自建下界：没有量级矛盾，倍数 = 周转率

- 34 天、classic 曲线净流入 **6.39M SOL ≈ $699M**（按 $109.35/SOL）
- 毛手续费下界 **$8.74M**（1.25%），协议下界 **$6.64M**（0.95%）
- DefiLlama 同窗口曲线费用 **$55.20M** → **DL 是毛下界的 6.3 倍**
- 日频周转倍数中位：09-09 前 **5.25×**，09-09 后 **6.01×**

这个倍数不是"差额"，而是"同一笔钱周转次数"的度量；它的**绝对值**受解码器缺口影响（09-27 前下界偏低 → 倍数偏高），**变化**则混入了 custom pairs 与费率调整两个因素。**要精确拆开，必须有内部数据。**

### 2.3 custom pairs 断点（他们的 bug 区间）

| 日期 | 非 SOL 发币占比 | 日周转倍数 |
|---|---|---|
| 09-01 ~ 09-08 | 3.2% ~ 5.7% | 4.2× ~ 6.2×（09-02 因数据未闭合为异常 13.8×） |
| **09-09** | **16.3%** | 5.36× |
| 09-10 ~ 10-03 | 6.3% ~ 22.2%（中位 ~10.5%） | 5.0× ~ 6.7× |

自定义交易对上线当天占比跳 3 倍以上——**看板的失真起点与产品上线时点完全重合**。公开数据能确认"缺口存在且量级可观"，但**无法回答"缺口值多少钱"**。

## 3. 若有内部数据，审计要回答的 7 个问题

1. **custom pairs 的费用如何入账**：曲线费、PumpSwap 费、结算资产（USDC/股票/PUMP）分别怎么计价与归集？
2. `fees.pump.fun` 的"年化"用的确切窗口与口径是什么（90d 均值？滚动？含不含 custom pairs）？
3. 50% 回购按哪个收入口径执行：毛/净、含不含 PumpSwap 的 0.05%、含不含 custom pairs？
4. PumpSwap 的协议分成（0.05%）是否 100% 进入回购池？
5. MoonPay 入金、Arkham/Houdini 等合作是否产生收入分成或成本，如何入账？
6. Mayhem 保险基金里的手续费如何处理（计入/不计入收入）？
7. 2026 年的创作者费改版后，创作者与协议的分成比例如何体现在收入里？

**交付形态**：一份可复算的对账报告 + 一套持续监控口径（日频，自动对比内部数 vs 公开数），不是新平台。

## 4.5 链上直读（L1，一手数据，不经过第三方）

2026-10-13 新增。官方在 `pump-fun/pump-public-docs` 公开了全部所需资源：

| 资源 | 内容 |
|---|---|
| `docs/FEE_RECIPIENTS.md` | **24 个费用收款地址**（8 normal + 8 mayhem 保留 + 8 buyback） |
| `idl/pump_fees.json` | 费用程序 IDL，程序 ID `pfeeUxB6jkeY1Hxd7CsFCAjcbHA9rWtchMGdZ6VojVZ` |
| `docs/FEE_PROGRAM_README.md` | 动态费率计算逻辑（按市值分层） |
| `docs/fees` | 完整费率表（曲线 / PumpSwap / 自定义交易对） |

**实测（公共 Solana RPC，`revenue_probe.py --snapshot`）**：normal 8 个地址合计
**91,489.9 SOL**、mayhem **135.1 SOL**、buyback **15.8 SOL**（buyback 基本实时扫走）。

**结构发现**：直接看收款地址的交易，大多数是「费用配置账户引用」而不是现金转账；
费用先进 **PDA**，再由程序指令（`sweep_buyback` / `claim_social_fee_pda` 等）扫描/申领。
所以精确重建收入需要**解码 pump_fees 指令与 PDA 账户**，而不是只看收款地址余额差。

**当前工具**：`revenue_probe.py`
- `--snapshot`：秒级读 24 个地址余额（可靠）
- `--hours N --sample M`：采样交易做入账/扫出估计（方法演示；公共 RPC 慢且采样噪声大）

**下一步工程量**（即审计服务的第一阶段）：
1. 从 IDL 派生 PDA，解码 `sweep_buyback` / claims，建立协议 / 回购 / 创作者三条日收入线
2. 付费 RPC 或 Geyser 流（公共 RPC 跑 8×30 笔就要 350 秒，无法全量）
3. custom pairs：跟踪 SPL 转账（USDC / 代币化股票）进入同一套收款/PDA 体系

## 4.6 A1+A2 实测结果（2026-10-13）

工具：`fee_program_probe.py`（`derive` / `scan` / `trades`）与 `revenue_probe.py`。

**已确认的机制**（官方 SDK 4.0.0 源码 + 链上交易双向验证）：

1. 每笔交易从 8 个 normal 收款地址**随机选 1 个**收协议费，从 8 个 buyback
   地址随机选 1 个收回购费；
2. 两者都以 **quote 资产**入账——SOL 池是 WSOL（`So1111…`），自定义交易对/
   币本位池是任意 SPL token；
3. 因此**收入碎片化在几十万个 token 账户上**：实测单个收款地址持有
   **25.7 万 ~ 57.1 万** 个 SPL token 账户。这就是官方看板在 custom pairs 上线
   后无法正确归集收入/回购的结构性原因。

**两条可写进提案的发现**：

- **发现 #1（公开资料与链上不一致）**：公开 docs 与 npm SDK 4.0.0 的 30 个
  指令判别码全部等于 `sha256("global:"+name)[:8]`（校验 30/30），但链上真实
  调用的费用程序指令判别码 `297ebd54ab49eeee` **不在其中**——部署版本与
  公开 ABI 存在缺口。精确解码需要他们确认版本，或按 SDK 历史版本对齐。
- **发现 #2（口径根源）**：收入不是「SOL 进一个钱包」而是「quote 资产进几十万
  个 ATA」。任何只数 SOL 余额或只看单一 USD 口径的看板都会失真；正确做法是
  按交易解码费率（分层表）再对 quote 资产定价。

**PDA 推导已验证**：纯 Python 实现（sha256 + ed25519 曲外校验）推出的
`fee-program-global` = `CHqnuTkj6sXDFknM652aEFPECZh9qVsBXWkhPohmV9dA`，链上存在。

**到「一手收入数字」还差**：① 匹配部署版本的 ABI（问他们或对齐 SDK 历史版）；
② 全量数据源（已支持付费 RPC，见下）；③ quote 资产定价层；④ creator fee（creator-vault /
sharing-config）路径。

**RPC 配置**（付费端点会自动优先使用）：

```bash
cp .env.example .env      # 填入 ALCHEMY_RPC_URL=https://solana-mainnet.g.alchemy.com/v2/<KEY>
python3 fee_program_probe.py --workers 32 --rate 0.004 trades --per-address 1000
```

`rpc.py` 是共享客户端：解析顺序 `--rpc` → `ALCHEMY_RPC_URL` → `SOLANA_RPC_URL` →
`RPC_URL` → `.env` → 公共端点；带全局限速与重试。

### 4.7 第一版链上入账（采样，2026-10-13）

用付费 Alchemy RPC 扫 24 个收款地址的交易（去重），聚合 quote 资产入账：

| 采样 | 去重交易 | 命中入账 | 窗口 | 可定价（WSOL/USDC） | 外推/天 | 不可定价 mint 数 |
|---|---|---|---|---|---|---|
| 每地址 250 笔 | 3,637 | 2,653 | 0.4 分钟 | $13.66 | ~$49k | 22 |
| 每地址 1000 笔 | 13,102 | 12,758 | 1.7 分钟 | $88.23 | ~$75k | 29 |

**读法（重要）**：两次采样同量级（$49k~$75k/天），但**仅为看板日收入的 3~4%**。
原因不是方法错，而是：

1. **可定价资产只占小头**：每笔采样只看到 WSOL/USDC 的少量入账；
   大头沉淀在 29~31 种长尾 quote 资产（自定义交易对 / 币本位池）里，**无现成价格**；
2. 采样窗口极短（收款地址每秒命中的交易太多）：全量需流式（Geyser/WebSocket）；
3. 同一笔交易中 normal 与 buyback 各取一份，部分 mint 两者数值几乎相等
   （如 `8sHq…` 257,425.596），可作为分账比例的直接证据。

**结论（写进提案的第三个发现）**：
> 即使直接读链，**没有明确的长尾 quote 资产定价政策，也算不出 USD 收入**——
> 定价口径本身就是一个必须向团队确认的方法论问题（对应接触材料的第 4 问）。

**定价后的第一版结果**（`price_flows.py`，DexScreener 定价全部 60 种 mint）：

| 角色 | 采样入账 USD | 占样本 |
|---|---|---|
| normal（协议费） | $209.45 | 47% |
| buyback（回购） | $240.18 | 53% |
| **合计** | **$449.63 / 1.7 分钟** | → **外推 $380,861/天** |

仍然低于看板的 ~$1.9M/天（约 20%），已知原因：
1. **采样窗口只有 102 秒**，且不是全天均匀采样（收款地址最近交易集中在某一时段）；
2. **只覆盖 24 个公开收款地址**：creator fee、social/donation PDA 等其他收入线不在内；
3. 只统计 token 账户变化，未含可能的原生 SOL 入账。

**下一步**：① Alchemy WebSocket（`logsSubscribe`）流式跑满一整天，彻底消除采样偏差；
② 加入 creator fee / social / donation 三条线；③ 定价后的日收入接入对照页第三条腿。
