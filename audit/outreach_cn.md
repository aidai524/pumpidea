# 接触材料（中文内部版）

英文对外版见 [`outreach_en.md`](./outreach_en.md)。这版给内部对齐用。

## 开场钩子

你们自己写在 `fees.pump.fun` 上的那句：「自定义交易对上线后，费用看板不再正确反映收入和回购。」
我们用公开链上数据把这件事独立复算了——**能量化，而且发现了两件你们团队可能有用的东西**。

## 两个发现（全部来自公开数据）

**1. 收入以 quote 资产形式散落在几十万个 token 账户里。**
每笔交易从 8 个公开 normal 收款地址里随机选 1 个收协议费、从 8 个 buyback 地址随机选 1 个收回购费，
以池子的 quote 资产入账（SOL 池 = WSOL，自定义交易对 = USDC / 任意代币）。
实测单个收款地址持有 **25.7 万 ~ 57.1 万个 SPL token 账户**。
要归集收入，就必须对几万种 quote 资产做聚合与定价——这是 custom pairs 之后看板难以保持正确的**结构性原因**。

**2. 公开的费用程序 ABI 与链上部署不一致。**
链上真实调用的费用程序指令判别码 `297ebd54ab49eeee`，
在公开的 `pump-public-docs/idl/pump_fees.json` 和所有 npm SDK（1.37.0 → 4.0.0）里都不存在
（30~31 个公开判别码全部符合 `sha256("global:"+name)[:8]`，没有一个匹配）。
是部署版本领先于公开 IDL，还是一条不对外暴露的内部指令？外部对账需要匹配的 ABI。

**3. 方法校验**：用 mint 级数据做的净流入下界 = 同期 DefiLlama 曲线费用的 ~16%，
与资金在曲线上的周转次数一致——没有矛盾，是可用的独立校验。

## 我们能提供的

- 从链上直接重建**协议 / 回购 / 创作者**三条日收入线（含 custom pairs），
  并给出明确的 quote 资产定价政策；
- 与官方看板、第三方聚合对账，把每一处差异归因到「时窗 / 范围 / 定价」；
- 交付可复现的管道（原始数据 → 标签 → 指标），他们的团队可以每天自己重跑；
- 附一套偏离报警脚本。

定位：**不替代他们的数据团队，而是提供一把不依赖他们自家账本的"外部尺子"。**

## 建议的第一步

2~3 周的付费诊断。先要一次 30 分钟通话（费用看板的负责人），
外加**单日导出**（CSV 或沙箱）用来把我们的链上重建与他们的账本对齐。

## 给他们的 7 个问题

1. 部署的费用程序版本是哪个？能否给匹配的 IDL？
2. 看板的收入口径（时窗、毛/净、是否含 custom pairs、quote 资产如何处理）？
3. 50% 回购基于哪个收入数字计算？
4. custom pairs 的 quote 资产按什么政策定价？
5. 创作者费与 Mayhem 保险基金如何计入收入？
6. PumpSwap 的 0.05% 协议分成是否进回购池？
7. 能否给单日的账本导出做验证？
